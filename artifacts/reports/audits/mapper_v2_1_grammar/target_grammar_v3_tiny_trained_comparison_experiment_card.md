# Target Grammar v3 Tiny Trained Comparison Experiment Card

## Mode

- Mode: planner
- Route: TEST
- Source idea: v3 now has representation, dataset/model/loss, incremental inference, inference rollout, and training runner smoke evidence. The next replacement blocker is a comparable trained report against v2.1.
- Acceptance source, if any: active goal requires v3 mapper full pipeline from training to inference before replacement.
- Source snapshot / evidence grade: strong representation evidence; medium trainability evidence; missing paired trained-comparison evidence.

## Hypothesis

A paired tiny training comparison can verify that v3 and v2.1 can be trained through comparable runner/report contracts on the same local slice, and that v3 keeps its target-length advantage after the training runner boundary.

## Root Objective

Create a reproducible comparison layer between v2.1 and v3 trained mapper reports before attempting longer training or session-runtime replacement.

## Goal Decomposition

- Subgoal 1: Define a report-level comparison harness that reads v2.1 and v3 shared-runner reports.
- Subgoal 2: Verify report contracts, completion, final eval loss, valid-token counts, and dataset counts.
- Subgoal 3: Run matched tiny v2.1/v3 training reports on the same local index.
- Subgoal 4: Record whether v3 preserves lower valid target-token count in the runner metrics.
- Subgoal 5: Keep v2.1 and v3 guard tests passing.

## Candidate Variants

- Variant A: Add a report comparison harness and run it on matched tiny training reports.
- Variant B: Launch longer 4K training immediately.
- Variant C: Compare only unit-test batch losses.
- Variant D: Move directly to session-runtime default replacement.

## Local Verification Matrix

- Variant A: Best fast-fail gate; it proves report compatibility and paired runner metrics without committing to a long run.
- Variant B: Rejected for this pass because it is expensive before the comparison harness exists.
- Variant C: Rejected because batch-loss tests do not prove checkpoint/report-level comparability.
- Variant D: Rejected because trained comparison evidence is still missing.

## Selected Variant

- Selected: Variant A, report comparison harness plus matched tiny real run comparison.

- Must preserve the v2.1 comparator path.

## Qualitative Check

Inspect the generated comparison report:

- expected contracts are explicit,
- valid-token ratio is reported,
- limitations state that this is not a quality result,
- next step is a longer bounded comparison only if the tiny gate passes.

## Positive Signal

- Comparison harness tests pass.
- Both tiny training reports complete.
- v3 has lower valid-token count than v2.1 on the matched tiny slice.
- v2.1 and v3 guard tests stay green.

## Negative Signal

- report schema mismatch,
- missing token contract,
- non-finite loss,
- v3 target-token count not lower even on matched examples,
- training smoke cannot produce either report.

## Kill Criteria

Kill immediate longer-training escalation if the comparison harness cannot validate contracts, losses, and token counts on matched tiny reports.

## Expected Failure Modes

- v2.1 tiny sample sequence may require a larger `max_seq_len` than v3.
- report schema may store metrics in different keys than expected.
- tiny results may be noisy and not interpretable as quality.
- local data/cache may be unavailable on another machine.

## Expected Runtime / Runtime Budget

Unit tests should run under 2 minutes. Matched tiny training and comparison should run under 10 minutes locally.

## Confounders

- One-step tiny losses do not measure convergence.
- Tiny slice may not include hard LN/chord cases.
- Different vocabulary sizes make raw per-token loss not a direct quality comparator.

## Result Interpretation Plan

- Positive: run a longer bounded v3-vs-v2.1 comparison with fixed train/eval split and comparable compute.
- Negative: repair runner/report comparability or revisit v3 training integration.
- Ambiguous: add a slightly larger slice before making a training decision.
